# Run the iPad real transfer diagnostic

This diagnostic selects a valid MKV in Explorer, sends it through unchanged Windows LocalSend 1.17.0, accepts it in an unchanged iPad LocalSend IPA, and compares the saved Documents file with the source. The separate signed Swift proxy forwards TLS bytes through BrowserStack Local. It has a finite iOS background budget.

The workflow runs one Windows Server 2022 x64 job in `ShlomoCode/localsend`. It requires an already uploaded proxy app URL, the receiver app URL, and the receiver's exact artifact provenance. Build and upload the proxy version that supports `/health` and `/ack` before dispatch. Enter immutable `bs://` hashes, rather than custom IDs that might later select another build. The workflow has no push trigger; the parent dispatches it after the source and helper-build gates.

1. Build the separate Swift proxy through its cloud workflow and upload that IPA normally to BrowserStack.
2. Dispatch `issue1591-realpair.yml` with its proxy hash and an unchanged receiver hash. Describe the receiver version, source or release lineage, and cloud build/upload reference in `receiver_identity`.
3. Leave `comparison` at `none` for the first run. Inspect Gallery off, Explorer selection, real approval/completion, the exact Documents pull, SHA-256, original device logs, video, and cleanup results.
4. After that control succeeds, select `mp4-off` to compare the same H.264/AAC streams in MP4. The workflow repeats the MKV control before the MP4 case.
5. Select `gallery-on` only after reviewing the working control. It runs the MKV Documents control, then an MP4 gallery control, then MKV gallery. It requests only normal add-only Photos consent. MP4 gallery completion is UI evidence; MKV's expected folder fallback requires the exact Documents hash. This diagnostic does not claim byte verification inside Photos.

For a baseline/fix comparison, set `fixture_run_id` and `fixture_artifact` to the retained fork run and exact evidence artifact. The job verifies the original source fixture identities, then selects copies with unique case filenames. This keeps media bytes/codecs identical and avoids destination collisions. Do not generate fresh fixtures for a causal comparison.

The Windows job encodes a one-second MP4 once with FFmpeg, then remuxes those streams into MKV. It retains FFmpeg/ffprobe versions, both stream/container reports, the source bytes, and SHA-256. Windows release archive and executable identities are recorded separately.

`windows-ui-server.ps1` loads and compiles the existing native Windows helper before switching to the receiver. A persistent owned PowerShell process then performs send clicks and screenshots without recompiling native types during the finite iOS background interval.

Authenticated `/health` samples record helper PID, generation, application state, elapsed time, remaining budget and per-peer ready/byte/EOF state. The relay adds server UTC and monotonic receive timestamps and keeps at most 1,800 samples. The controller requires an active/running sample before switching; after activation it requires the same helper PID/generation, fresh background state, positive finite budget after subtracting sample age, and LocalSend Appium state 4. It checks these at send, Accept, save and Documents-pull milestones and latches health faults while remote UI commands run. The five-second freshness threshold is an explicit diagnostic threshold; it does not promise any iOS background duration.

Before the Windows send actions, the controller requires an observed adjusted allowance of at least 20 seconds; before **Accept**, it requires at least 15 seconds. The fixture is one second long, but media duration does not bound transfer or remote UI latency. These margins subtract server sample age, not unknown device-to-server transit time. UI calls have their own finite deadlines and can still outlast the available allowance. Live health faults and original native expiry/poll/push/health failures before the owned stop invalidate the run.

Pull events carry ordered sequence IDs. The relay retains each batch until the helper acknowledges its final ID after consuming every event and awaiting native send callbacks. Lost or ambiguous ACKs fail the helper; no batch retry can duplicate bytes. Device-to-sender accounting increases only after a successful socket-write callback. Transport faults, per-peer directional counts and timestamps are retained and block application-error interpretation.

At case end, a bounded five-second audit requires no pending ACK, zero queued bytes and per-peer acknowledged bytes equal to sender bytes while health remains qualified. Its timestamped observations are retained. This is an observed transport boundary; parent review still must establish the sender's actual result.

Each run admits at most one owned BrowserStack session after a fresh capacity check against the five-session ceiling and plan limits. It stores only its own session ID and deletes only that session, without a trailing slash. It stops its owned Local process tree and relay in `finally`. Failures remain workflow failures; a missing element, unsupported pull, tunnel failure, suspension, or expiry is not labeled a product reproduction.

Evidence includes W3C HTTP status/errors, native source and screenshots, Windows selection/menu/input and sender-end records, saved bytes, transport trace, background-switch timestamps, original device/Appium logs, original BrowserStack video, and cleanup status. Missing or failed original evidence retrieval fails the job. Receiver success requires an observed **Finished** file result in addition to **Done**. The Windows backend supplies original screenshots and HWND/PID/input records; its sender status requires visual review because Flutter text is not exposed by that backend. Results retain `senderVerified=false` and require parent admission; a controller exit of zero is not a claim that both endpoints succeeded. The relay token is ephemeral and redacted from persisted text. BrowserStack's retained Appium service logs can include UI value RPCs, so the token is usable only during its owned run and the relay is stopped on completion.
