# Android sender for issue 3441

This diagnostic stages generated media through a separate public MediaStore helper and drives the unmodified LocalSend 1.18.2 app through its Media picker. Run it only in an admitted ShlomoCode/localsend Actions job. These instructions describe the source gates; they do not claim that a source revision has passed an execution.

The receiver worker supplies `fixtures/manifest.json`, 208 valid JPEG/MP4 source files, and the real macOS receiver. The cases are a separate one-file control, 207 media files, then the same 73 original sources totaling 85,600,000 bytes. Source names are distinct. The helper moves the same MediaStore URIs between case albums; it does not create new retry content. Destination duplicates are observed by the receiver rather than assumed.

The manifest contract is `{files:[{name,mimeType,bytes,sha256}],cases:[{id,names}]}`. Case IDs must appear in order: `control`, `initial207`, `retry73`. The native helper reads each staged URI back, verifies its bytes and SHA-256, decodes its JPEG or MP4 frame, and exposes all receipts in its UI. The controller requires one complete receipt, the exact ordered source names, and distinct native URIs. It reads both single-quoted and double-quoted XML attributes, including encoded newlines. The helper also records native manufacturer/model/display/fingerprint/security patch and an optional bounded raw `ro.build.version.oneui` observation. An unavailable property is explicitly unknown; Android 13 and the model do not establish One UI 5.1. The controller retains the receipts and the observed media index, title, bounds, selection order, selected count, LocalSend count/size summary, and terminal labels.

After root resource admission and the coordinator opens the cloud window, the integrated cloud job must:

1. Generate and decode the fixtures with `support/diagnostics/3441/fixtures.mjs`.
2. Download the official arm64 1.18.2 APK, verify 46,558,706 bytes and SHA-256 `82ec3568fba2aa5295b9aae8b76f701d7a4703d86b9f8bad749472038fbaeab3`, and upload those verified bytes. Retain `original-android-apk.json` with `sha256`, `bytes`, and `uploadReferenceSha256`. An older uploaded reference without this binding does not meet the gate.
3. Run `bash support/diagnostics/3441-android/build-helpers.sh` with `FIXTURE_DIRECTORY`, `RELAY_TOKEN`, Android SDK variables, and BrowserStack credentials. This emits `HELPER_APP` and `RELAY_APP` to `GITHUB_ENV` and retains byte hashes plus upload-reference hashes. Keep private helper APKs and transport configuration outside uploaded evidence.
4. Supply a cloud `BROWSERSTACK_LOCAL_BINARY`, `BASELINE_APP`, `BS_LOCAL_ID`, and `ISSUE3441_ADMITTED=1` only after resource, budget, and cleanup review. Set `ISSUE3441_JOB_DEADLINE_UTC` at the start of the job to its real 45-minute deadline. The controller subtracts prior preparation time, stops scenarios at minute 35, and stops its own cleanup/provider retention by minute 37. The remaining eight minutes cover independent Android cleanup, native capture/signature cleanup, and artifact upload. It records stage age, remaining time, and observation counters and refuses a case when the remaining time cannot admit its selection/send. It checks fresh shared capacity and creates at most one Samsung Galaxy S23 Android 13 session with a unique run/attempt build name.
5. Invoke `runAndroidSender({output,fixtureDirectory,receiver})` from the receiver orchestration. The receiver exposes `startCase(id)` and `finishCase()`. Start its opaque relay before calling the controller and stop it afterward.

Each cloud attempt must inspect any unverified UI assumptions. Picker behavior is grounded in the source's accessible asset title/index and selected state, but the Samsung Media picker hierarchy has not been observed yet. After activation, the controller requires two matching observations of the active package, PORTRAIT orientation, and portrait root/window geometry. Before a touch, it re-finds the exact enabled visible control, checks its entire bounds and center against the observed geometry, and retains the pre-action XML. Critical controls also retain a screenshot followed by another exact-control observation. Coordinates are never scaled or remapped. Unexpected layout, picker, permission, or favorite controls fail the diagnostic and preserve evidence; they do not become app-failure evidence. The controller checks a 207/73 picker count before confirmation and the corresponding LocalSend file count before Send. Helper start observations retain lifecycle/request failures separately from the touch and transport claims.

The one-file control must pass both the original sender and the receiver's actual Accept/save/hash check before larger cases proceed. After that control passes, a batch sender error is retained and the controller continues to the same 73-source retry. Such an error differs from the report's successful Finished display and is a discriminating observation, not reproduction of that display/content discrepancy. Initial and retry results retain the receiver's complete before/after destination inventories, approval observations, and hashes. A Finished label alone does not establish successful content. The cloud route, Android model, One UI version, generated sources, and macOS version differ from the report; the original picker path, actual media, source/destination hashes, and exact Samsung model remain unavailable.

The controller requests provider video for the whole Appium session, including helper staging and actual LocalSend selection/Finished screens. Probe/decode each have a 30-second bound and must fit the remaining cleanup reserve. A recognizable but unvalidated candidate is named separately. Readable coverage of the app actions still requires inspecting the corresponding original frames; helper footage or a configured video flag does not prove that coverage. It checks the persisted tunnel PID, process start/command identity, executable, and unique local identifier before sending a termination signal. The workflow runs it before native cleanup and artifact upload, preserving unrelated sessions, processes, and files.
