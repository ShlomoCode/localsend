# Issue 3556 native TCP gate

Manual, fork-only Windows Server 2022 workflow. The parent must reserve this issue's one BrowserStack session before dispatch; the cloud controller refreshes the device catalog and verifies a free account slot immediately before creating the session. Shared workflow concurrency prevents overlapping issue 3556 diagnostic jobs. Other issues may use the remaining account capacity.

The job builds and privately uploads a separate native helper, then opens one physical Samsung Galaxy S20 / Android 10 App Automate session with one owned BrowserStack Local process. It does not build, modify, or launch LocalSend. The helper starts only after the controller observes and touches its native button.

The workflow selects one concrete RFC 1918 IPv4 address from an active Windows adapter with an IPv4 default gateway, ordered by interface index then address. It records the local adapter inventory and selection without scanning any remote address. Both runner listeners bind that exact address; the same address is embedded in the helper. The helper first authenticates to `http://<selected-address>:8080/health` and checks the fresh embedded run marker through BrowserStack Local with forceLocal. It then runs native DNS resolution on that literal address, records the answer and requires it to match, and connects a native Socket to the identical address on port 53317 with a ten-second connect bound. A successful HTTP probe does not establish raw TCP support.

Each of the deterministic 0, 1 and 65,537-byte cases flushes and half-closes Android output. The real runner listener on `<selected-address>:53317` records its local socket address, byte count, SHA-256 and readable EOF, writes a JSON response containing the fresh marker/count/hash, flushes, then half-closes output. Android reads through EOF and verifies all three values. Read deadlines and a 25-second per-case socket-close watchdog bound stalled cases; DNS has a ten-second future deadline. The controller stops on the first native failure and never starts a larger transfer.

Artifacts include native phases/timestamps, exception class and redacted message, observed XML and screenshots, authenticated HTTP evidence, native DNS and connect evidence, actual listener addresses, adapter selection, runner EOF/hash records, provider admission, and cleanup results. The owned Local process has an exit listener installed immediately after spawn; cleanup records its PID, exit code and termination signal. Signal termination can legitimately have a null exit code, so cleanup uses the captured exit event instead. Credentials, authentication token, and private uploaded-app references are redacted. The capability-bearing APK remains in runner temporary storage and is deleted after use; it is never an evidence artifact.

Run syntax checks, Java compilation and all runtime validation only in this owned Actions job. A pass is a tiny synthetic transport result, not an original-app reproduction, sustained-throughput result, or 16 GB result. The runner OS differs from the reported Windows 10 environment; the reporter's Android OS is unknown. The parent may separately authorize an original-app 64 MiB direct-path gate after reviewing a pass, or investigate a streaming diagnostic HTTP transport after a failure.

## Next transport proposal if this address also fails

Implement a diagnostic relay change separately: authenticate and acknowledge the existing peer-open operation, then send opaque Android-to-runner bytes in one chunked binary HTTP POST per peer. Keep reverse pull delivery active in an independent worker while that POST remains open, because LocalSend TLS/HTTP keepalive may outlive the visible file transfer. Pipe the POST into the runner socket with backpressure; only request EOF half-closes TCP output. Cancellation or HTTP failure destroys only its owned peer and reports the failed phase. Preserve certificates and application bytes; remove serial Base64/JSON request round trips from the upload data path.

Before using real apps, verify 0/1/65,537-byte counts/hashes, EOF-before-reply, simultaneous reverse response during an open upload, bounded queue/backpressure, and cancellation. Set a finite request timeout above the planned transfer duration, with finite progress and absolute deadlines, then include a stream lasting over five minutes to expose Node's usual 300-second request limit. Follow with the exact original-app 64 MiB send/Windows save/hash gate and measure both relay throughput and send-to-verified-save elapsed time. Use those measurements and the verified provider session window to decide any larger transfer. This paragraph is a proposal; this workflow implements none of it.
