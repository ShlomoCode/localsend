## Single sequence for each arm

The source-only `pair-sequence.mjs` starts after ordinary setup reaches an unselected portrait picker. Both arms run the exact same source and delays. It records command-start events before sending requests, so pending work remains visible, and saves raw end/error responses and UTC timings.

1. Verify one visible sample, portrait402×874 and Confirm disabled. Derive image/Close centers from the live working control. Tap the sample and verify Confirm1 enabled; tap Close and verify Send. Reopen Media and verify an unselected one-sample picker again. This is a control, not a selected-item prerequisite for the trigger.
2. From this unselected Media picker, rotate landscape, hold2s, return portrait, hold2s. Do not query postrotation native XML or issue a separate screenshot before the raw input attempts. Existing provider debug capture still runs and must be disclosed.
3. Tap the image at its last independently observed portrait center, hold1s, tap Close at its observed portrait center, hold1s. The continuous provider recording and command timing must be inspected for actual selection/Close response. A successful command return alone is not an app-behavior pass. Wrong returned geometry or a missed coordinate is not whole-app deadlock evidence.
4. Read native XML after the raw Close attempt. Require Send/Media for the scripted completion gate. If available, reopen, select the same sample, verify Confirm1, confirm and verify Send Files1. This tests app progress after the one rotation and is not a second rotation trial.

This intentionally changes the old default observation order: previously the first postlandscape source request timed out before any postrotation selection/Close was executed. The new order completes the reported landscape→portrait input before the first explicit postrotation source read. It addresses the missing app-input observation but is a shared harness change, not a bit-for-bit replay of that prior failed snapshot condition. Neither an XML failure alone nor distorted provider video proves the reported whole-app freeze. Current debug=true capture may itself request native screenshots; WDA/provider effects remain possible.

## Failure routing and cleanup

No automatic three repetitions. Run exactly one rotation condition per arm. If an arm's control/setup fails, preserve the evidence and stop the pair. A returned proxy/gateway/WDA timeout, transport failure, malformed response or client abort does not establish that underlying native work has settled. Mark that state unresolved, stop the pair and enter owned-session cleanup; do not probe recovery by queuing terminate/install. A baseline failure can continue to the candidate only when it is an observable-behavior assertion after successful native responses, the intended trigger was reached, and the supported termination acknowledges completion followed by queryAppState confirming the old target is not running. Any provider/native error during this transition stops the pair. No changed Appium idle settings, sleeps tuned until success, new devices or replacement build.

The candidate cannot be declared a paired improvement unless both working controls and both intended triggers were reached. Stop on any unsupported install or same-session identity mismatch. The proposed fork workflow and coordinator are now concrete source in `proposed-workflow.yml` and `pair-coordinator.mjs`; neither is adopted or executed. A first workflow step records the absolute clock before checkout, SDK setup and archive preparation. One shared 20-minute scenario deadline includes that preparation, uploads, acquisition, setup, installation and replay. The final five minutes of the 25-minute job are reserved for cleanup/evidence: coordinator operations finish by minute24, leaving the final minute for artifact upload. The sequence refuses to start a native request unless its full 300-second provider-timeout allowance fits before the shared scenario deadline; no fresh per-arm deadline extends the allocation. Hard cancellation can interrupt cleanup, so missing release receipts leave ownership unknown and require root reconciliation. It is not runnable locally. Root must review the final sources and supply a fresh nonce/source-SHA/ref-bound admission after sibling coordination; capacity is rechecked immediately before allocation. Credential values stay in configured secrets/environment and are never stored in public evidence.

The proposed secret names `BROWSERSTACK_USERNAME` and `BROWSERSTACK_ACCESS_KEY` are not yet verified in the fork. Exact iOS18.6 allocation, provider signing, native screenshot support and non-skipped same-version installation remain runtime gates. Installation acknowledgment is provisional: retained provider logs must tie the exact candidate URL to a completed non-skipped install before any candidate comparison is accepted. Neither version58 nor an acknowledged API call independently proves installed bytes. These requirements authorize no provider operation at this source-only checkpoint.

Retain continuous original video, device/Appium logs, request-start/end timing, per-arm XML, uploaded app references, install lifecycle, process identity when supplied, capacity/admission and session-release receipts. Existing native resource reports may be retrieved if the provider supplies them; do not add a rebuild or symbol hunt. Mark invalid placeholder screenshots and compositor uncertainty. CPU resource events are not crash/deadlock reports.

After either outcome, release only the owned session through the canonical DELETE endpoint, verify the provider receipt/final stopped status and report zero ownership. Retrieve final evidence through existing read-only session URLs without exposing signed URLs/credentials. If cleanup is uncertain, keep ownership visible and escalate to root rather than allocate another device. Always preserve original artifacts and failed phases.

## Interpretation

A failing default and responsive candidate would show different responsiveness between these retained artifacts under this provider condition, compatible with the UI-thread configuration hypothesis. It would not attribute that difference to scheduling, identify an original Flutter fixing commit, prove renderer causality, eliminate the unattributed AOT byte difference, establish positive runtime thread identity, or reproduce the iOS18.4.1 App Store report. Fixed default→candidate ordering and fresh-install→upgrade state are additional causal limits.

If both pass, the prior failed native-query condition is not reproduced under this changed observation order; do not conclude the original issue is fixed or WDA is definitively the cause. If both fail, the supported false flag is insufficient for this condition. If a control, installation or observation fails, report the exact unexecuted requirement. Root decides whether a further discriminator is warranted; this proposal authorizes no follow-up matrix.
