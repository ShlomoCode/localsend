# Issue 3556 transfer path research (read-only, 2026-10-11)

## Observed control

The original LocalSend 1.18.2 Android app sent an exact 67,108,864-byte MP4 to the Windows receiver. The saved SHA-256 matched `ef75a7f173204678fa2fe8ff8c2bc37f5af84dc8d991dd40aeebcce982b8ce8c`; the Android UI finished, and the Windows UI accepted and saved it. Evidence: `../run-38137694346/windows-transfer/app-control-results.json`, `windows/results.json`, and `relay-final-status.json`. This is a 64 MiB control, not a 16 GB reproduction.

The upload peer `android-6` carried 67,203,849 TCP bytes in 1,028 Android-to-runner chunks, with a 65,536-byte maximum. Its first and last bytes were 48,055.98 ms apart: 1.398 MB/s at the relay. The app-send-to-verified-save interval was 51,252 ms: 1.309 MB/s of file payload. `paused=0`, peak queued bytes 1,264; queue backpressure was not the observed bottleneck.

`RelayService.readSocket` performs one synchronous `POST /push` per read, Base64-encodes the bytes in JSON, waits for a complete HTTP response, and only then reads the next chunk. `request` creates and disconnects an `HttpURLConnection` for each chunk. `relay.mjs` decodes the Base64 and writes to the Windows TCP peer; the response ends after the local write callback. This serial request/response path plausibly explains the roughly 46.7 ms per chunk (48.056 s / 1,028), though the run lacks per-request timestamps, so latency dominance is a strong hypothesis rather than a proven decomposition. Base64 expands the 67.2 MB wire data to at least 89.6 MB before JSON/HTTP framing.

At measured rate, 16 decimal GB would take roughly 3.18 hours for stream bytes or 3.40 hours using the end-to-end file rate; 16 GiB would take 3.42 or 3.65 hours. This linear projection excludes startup, stalls and post-transfer verification. The current Windows Actions job sets `timeout-minutes: 45`, so merely selecting a larger fixture cannot fit under the measured rate.

## Options, in priority order

1. **Prove direct native TCP through BrowserStack Local with a tiny transport control.** BrowserStack documents Local access from mobile apps to CI/private servers and `forceLocal`, but the retrieved docs do not expressly promise arbitrary raw TCP forwarding. The present successful path targets Android `127.0.0.1:53318` and sends helper HTTP to the Windows relay; it does not establish raw TCP reachability from the device to the runner. A single owned helper-to-runner test on a normal non-loopback hostname/IP and port should send 0, 1 and 65,537 byte half-close/reply cases and hash both ends. If it passes, set the unmodified app's receiver favorite to the runner address and 53317, with the original Windows receiver and TLS/mutual-certificate identity; no helper on the data path. Do not infer support from HTTP Local alone. A direct path is the largest potential speedup and closest to the reported LAN topology, but its reachability remains unproved.

   A single cloud job can discriminate cleanly: start one owned Local tunnel and one device session, bind a runner test listener on the intended port/address, and have the helper report DNS resolution, chosen address, connect result, byte counts, hashes, and half-close/reply completion. Check an ordinary HTTP request to the same configured runner hostname first to establish that the tunnel and name mapping are active; then try the raw `Socket` to that hostname and port. Do not use Android `127.0.0.1` as a surrogate for the runner or assume a BrowserStack Local hostname convention without verifying its Android behavior. A raw TCP connect failure after the HTTP control passes identifies a protocol/routing boundary; a DNS or HTTP failure is an address/tunnel setup failure and says nothing about raw TCP support. Stop after these small cases, record the exact failed phase, and release the owned session/tunnel without launching the original app transfer on a failed control. A pass proves reachability and stream semantics, not 16 GB throughput.

2. **If direct TCP fails, change only the diagnostic relay's upload data path to one chunked binary HTTP POST per TCP peer.** Keep the authenticated `/push` open command and the reverse `/pull` direction. After `open` is acknowledged, Android streams opaque bytes from the existing socket into `HttpURLConnection` with chunked transfer mode; Node pipes the request to that peer with backpressure. Only HTTP request EOF becomes TCP `end()`; cancellation/HTTP failure destroys just that peer and reports error. This removes 1,028 serial round trips and Base64/JSON expansion while leaving LocalSend's own bytes and certificates untouched. It requires explicit ordered open/data/eof handling, bounded buffering, and cancellation tests. Run existing 0/1/65,537-byte half-close/reply controls, then the exact real 64 MiB app-to-app save/hash gate before any larger fixture. Measure sustained MB/s and device/runner elapsed time. This is a proposal, not an implemented or validated improvement.

   Compatibility caveat: LocalSend's TLS socket can remain open for HTTP keepalive after the file upload and response. Thus one helper `HttpURLConnection` POST can also remain open after the visible transfer is finished, and waiting for its response before delivering the receiver's bytes would deadlock the protocol. The `/pull` loop must run independently and write receiver data to the Android socket while the streaming POST is still active. A per-peer upload worker must own cancellation and close/error propagation; an intentional TCP half-close is distinct from closing both directions. The relay must not infer TCP EOF from a quiet period after the file bytes, because that would break keepalive and later protocol traffic.

   Node 22's HTTP `server.requestTimeout` governs receipt of the entire request and commonly defaults to 300 seconds; an hours-long chunked POST therefore needs an explicit finite server limit above the planned test duration, plus a bounded per-peer progress/absolute-deadline watchdog and cleanup. Leaving every request unlimited globally would hide a hung peer; retaining the default may return 408 partway through a legitimate large stream. Keep headers and authentication bounded, and separately test a stream longer than five minutes before relying on the design for a 16 GB run.

3. **Duration increase is secondary.** The 45-minute cap is local workflow configuration, not evidence of a GitHub platform cap. BrowserStack's App Automate documentation describes a 2-hour maximum session, while its idle-timeout page says the `browserstack.idleTimeout` value can be raised to at most 300 seconds. `appium:newCommandTimeout`/heartbeat commands address idleness, not an absolute session limit. A longer Actions job alone cannot establish a 3.2–3.7-hour device session. If a revised path demonstrates enough speed for the verified provider window, increase the job timeout with appropriate margin; do not use a timeout change as the transport plan.

## Next decision gate

No 16 GB run should be dispatched from the current throughput projection. First test raw TCP reachability using the owned fork/BrowserStack allowance if selected by the parent. Otherwise implement the binary stream relay, prove the existing transport edge cases, repeat the real original-app 64 MiB control, and extrapolate from measured throughput to an allowed session duration with setup and verification margin. Preserve the original 1.18.2 APK, TLS/mutual-cert identity, byte order, half-close and cancellation behavior. The physical S20/Android 10 and Windows Server 2022 still differ from the reported Windows 10 shared LAN case.

## Current documentation consulted

- [BrowserStack App Automate Local testing](https://www.browserstack.com/docs/app-automate/appium/getting-started/nodejs/cucumber-js/local-testing): mobile apps can access local/CI/private servers; `forcelocal` can route traffic through the Local tunnel. It does not establish raw TCP support.
- [BrowserStack Local Node.js options](https://github.com/browserstack/browserstack-local-nodejs/blob/master/_autodocs/types.md): `forceLocal`, `onlyAutomate`, and `localIdentifier` are documented options.
- [BrowserStack App Automate idle timeout](https://www.browserstack.com/docs/app-automate/appium/troubleshooting/browserstack-idle-timeout): idle timeout maximum 300 seconds.
- [BrowserStack App Automate session timeout](https://www.browserstack.com/docs/app-automate/flutter-ios/timeouts): stated 2-hour maximum single session (Flutter/iOS page; verify against the specific Appium Android account before relying on it).
- [Node 22 HTTP server timeouts](https://nodejs.org/docs/latest-v22.x/api/http.html#serverrequesttimeout): `requestTimeout` limits receipt of the entire request; an expiry returns 408 and closes the connection. `server.setTimeout` is a separate inactivity setting.
