# Proposed 1 GiB desktop experiment

Status: research and concrete plan only. Do not dispatch until the current job has finished and the coordinator has reviewed this plan. No harness implementation or application execution was performed for this document.

## Supported environment and limits

Use an installed Debian 12 amd64 system with Openbox and **ordinary disk swap enabled**, two virtual CPUs, and 1024 MiB physical guest RAM. Debian's official amd64 installer guide lists a desktop minimum of 1 gigabyte, recommends 2 gigabytes, and explicitly conditions its minimum on swap and an installed, non-live system: “The minimum values assumes that swap will be enabled and a non-liveCD image is used.” It also recommends lighter window managers for low-end systems. This supports a conditional minimum-spec desktop experiment; it is not a guarantee that LocalSend or a 5000-file workload fits. The source says gigabytes, not GiB, so retain its wording and separately report the configured 1024 MiB and measured MemTotal. [Debian 12 hardware requirements](https://www.debian.org/releases/bookworm/amd64/ch03s04.en.html)

Openbox is packaged by Debian and described as a lightweight window manager capable of operating as a standalone environment. Selecting it is a reasonable implementation of the lightweight-desktop advice, not a separately documented Openbox-specific 1 GiB guarantee. Use the distribution's normal packages, X server, session D-Bus, GTK runtime, and software rendering configuration; record their exact versions. [Debian Openbox package](https://packages.debian.org/bookworm/openbox)

Do not claim that the current Ubuntu 24.04 Server cloud image plus Openbox is an officially documented 1 GiB Ubuntu Desktop configuration. It is not the standard GNOME desktop image. The versioned Canonical installation guide does not establish a 1 GiB minimum for this custom configuration, and Ubuntu community desktop guidance cannot establish it for Server plus Openbox either. A bootable Ubuntu image is also not evidence that the desktop/application workload meets a supported minimum. [Ubuntu 24.04 Desktop installation guide](https://ubuntu.com/desktop/docs/en/24.04/tutorial/install-ubuntu-desktop/)

Debian instead of Ubuntu changes the kernel, libc, GTK/Mesa packages, and background services. Ordinary swap also differs from the earlier swap-free guest. Any comparison with the Ubuntu 2 GiB runs therefore has explicit OS/runtime/swap confounds. Counts 5, 500, and 5000 within the new Debian environment use the same OS, physical RAM, swap, packages, rendering, and instrumentation; this can associate growth with file count, without isolating a particular implementation cause. This is not a reconstruction of an unverified reporter RAM specification.

## Released binary compatibility

Use the same unmodified v1.17.0 x86-64 TAR on the host sender and guest receiver. Release URL: [LocalSend 1.17.0 Linux TAR](https://github.com/localsend/localsend/releases/download/v1.17.0/LocalSend-1.17.0-linux-x86-64.tar.gz). Expected SHA-256: `6f05e851b72dbeaac764d3446b5a61c34db22f6278baa92607d5b080997f8c81`.

A read-only download and static `llvm-readelf --version-info` / `--dynamic` inspection was completed locally; nothing from the archive was executed. Its SHA matches the previous runs. All sixteen ELF files (executable plus fifteen bundled shared objects) were inspected. The largest observed required GLIBC version is **2.29**, in `lib/librhttp.so`; the Flutter engine requires at most 2.18. The largest observed GLIBCXX requirement is **3.4.21**, in `lib/libopen_dir_linux_plugin.so`. Debian Bookworm's official libc6 package is glibc **2.36**, which clears the observed glibc version floor. This is necessary compatibility evidence, not proof that every dependency or runtime behavior works. [Debian libc6 package](https://packages.debian.org/bookworm/libc6)

Before launching any guest application, retain the artifact hash, ELF architecture/interpreter, full version-needs and DT_NEEDED output for every ELF. Match required symbol versions against the guest libraries, including GLIBCXX/CXXABI, and resolve all required SONAMEs against installed packages and bundled libraries. In particular the release needs GTK3, GLib/GIO, Pango/Cairo, HarfBuzz, ATK, GdkPixbuf, fontconfig, epoxy, libstdc++, and the tray plugin's `libayatana-appindicator3.so.1` and `libdbusmenu-glib.so.4`. Include libraries loaded at runtime such as EGL/GL/Mesa and libsecret in the package preflight. Do not rely on build-runner naming or `ldd` as the sole proof; use static inspection and guest library/package inventories. A missing symbol, loader, dependency, or initialization failure stops the test as setup/compatibility failure.

## Environment gate and case sequence

Prepare a non-live installed Debian image from verified official media. Use a normal 24 GiB disk with a fixed **2 GiB ordinary disk swap partition/file**, active from boot, at default distribution swap policy. Record media hash, disk filesystem/backing, `swapon --show`, swap size, kernel, package inventory, CPU, RAM, renderer, and idle desktop memory. Do not tune swap to induce failure, use RAM-backed swap, impose process/cgroup limits, create artificial pressure, or modify kernel OOM preferences. Install dependencies before observation and wait for package/cloud setup to finish.

Keep the sender on the ordinary external host desktop. Start a fresh guest receiver process and clean receiver settings/destination for each count; record its PID, starttime, launch status, stderr, and subsequent exit status. Wait for an ordinary ready desktop and application window before proceeding. Keep the same network topology and actual LocalSend protocol port. A new process avoids retained application heap from the previous case; remaining OS caches must be recorded rather than described as fully fresh system state. For stronger isolation, reboot the prepared guest between cases without changing its configuration.

1. **Five-file qualification:** Use the actual host folder picker to select five real files, Send the real metadata request, observe receiver approval, open Options, observe the rows, use Back, then Accept and complete the five-file save once. Verify exact names and all bytes, observe Finished, and record kernel/memory/process evidence. The desktop, launch, approval, Options, Back, and full control transfer must all work without OOM or process loss. If any fails, stop before 500/5000. Report that the environment/application control did not qualify; do not reclassify it as a large-count regression or force it through.
2. **500 files:** Start a fresh receiver (prefer a guest reboot), begin cheap sampling before the real metadata request, send the actual selected folder, observe approval, open Options, retain the pre-Accept measurements, hold for ten seconds, then Back and normal Cancel. Do not Accept or save the 500-file payload.
3. **5000 files:** Repeat the same sequence with a fresh receiver and the same observer. Do not Accept or save the 5000-file payload. If the 500-file case terminates the app or leaves the desktop unstable, preserve evidence and stop; a larger case is not needed to qualify that failure.

Options is reached **after the sender sends metadata**, but before receiver Accept/file payload transfer. Describe this precisely as pre-Accept Options observation, not as before all Send activity.

Each fixture is the same real 49-byte file content already used: `LocalSend issue 2414 fixed ordinary file content` followed by a newline. Use `Case2414Files5`, `Case2414Files500`, and `Case2414Files5000`, with `file-00000.txt` through the appropriate final index, on the external host. Retain count, exact-name manifest, size, and content hashes before the picker operation. Use real folder selection, request, and receiver UI; do not inject fake receive state or allocate dummy memory. Keep the existing expected content SHA-256 `6632a5e5b167e55fdbbb9e3ad38fd7ff042e66b620a00fb744b0d7f7e21534fb`.

## Low-cost observation

One persistent guest sampler runs every **0.5 seconds**, starting five seconds before the metadata request and ending after Cancel/process exit. Read only aggregate process `/proc/PID/stat`, `/proc/PID/status`, `/proc/meminfo`, selected `/proc/vmstat` counters (`pswpin`, `pswpout`, fault counters), and `/proc/pressure/memory`. Retain sampler PID CPU/RSS too. Do not enumerate every thread or run external capture commands periodically. CPU deltas use aggregate process utime/stime and real monotonic intervals; keep starttime to detect PID reuse. Sampling and handling of missing PID must survive process termination.

Collect `/proc/PID/smaps_rollup` at named stages: ready baseline, approval, Options entry, and approximately 1, 5, and 10 seconds after Options, plus immediately before normal Cancel. Retain RSS/PSS, process VmSwap, smaps Swap/SwapPss, MemAvailable, SwapTotal/SwapFree, swap-in/out deltas, and memory PSI. PSS collection is relatively more costly; timestamp each read and record its duration rather than assuming a free 2 Hz PSS observer. If 0.5-second PSS is later required, first measure its cost during the five-file control and apply exactly the same schedule to every count.

Take screenshots only at stages: application ready, picker-selected folder, approval, Options, Options after the ten-second hold, Back/Cancel, and five-file Finished. Retain capture start/end timestamps. A bounded readiness retry may take a small number of additional screenshots; record each cost and retry. No 10 Hz screenshot observer, no xinput observer, and no OCR/SCP during the measured window. Analyze copied artifacts/OCR afterward. Retain baseline and final kernel journals with monotonic timestamps and PID-relevant entries, plus serial/desktop logs; do not clear the kernel journal.

## Outcome rules

Compare each case's increment from its own ready/pre-metadata baseline to approval and Options peak PSS/RSS/SwapPss, available RAM, swap activity, PSI, and aggregate CPU. Peak RSS is not unique memory ownership, and filesystem cache is not proof of an application leak. A 1 GiB guest may swap and remain alive; ordinary swap is part of the qualified configuration and makes an OOM outcome uncertain.

Record UI deadlines as observation limits. A missed Options/readiness deadline with the same PID alive is **unknown cause / UI stage not observed**, not an OOM or permanent hang. Confirm an OOM only with a matching kernel victim event and PID/starttime/time correlation. Preserve process disappearance, exit code or signal, stderr, and kernel evidence separately; disappearance without a kernel OOM entry is not sufficient for an OOM claim. If the normal cancellation cannot be observed, preserve the state and stop rather than repeatedly injecting actions. A timeout-driven cleanup kill must be labeled harness cleanup and kept distinct from application/kernel termination.

The planned result is a qualified 1 GiB desktop control plus pre-Accept memory/CPU scaling evidence at 500 and 5000 real files. It is not a full-save benchmark, a promise to trigger OOM, a causal Ubuntu-versus-Debian RAM comparison, or a claim about the original reporter's device.
